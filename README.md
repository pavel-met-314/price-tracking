# Otsled — отслеживание цен allureparfum.ru

Небольшое Android-приложение (Kotlin + Compose, без сторонних DI-фреймворков), которое следит
за ценой ароматов на `allureparfum.ru`: хранит историю по объёмам, уведомляет об изменении
и о достижении желаемой цены, проверяет сайт в фоне.

## Сборка

```bash
./gradlew :app:assembleDebug      # APK в app/build/outputs/apk/debug/
./gradlew :app:testDebugUnitTest  # юнит-тесты парсера и логики
python3 tools/kt_check.py         # скобки, комментарии и `(?iu)` в регулярках — до отправки в CI
```

CI (`.github/workflows/ci.yml`) выполняет обе gradle-команды на каждый push, поэтому локальный
Android SDK не обязателен. `tools/kt_check.py` ловит ровно тот класс ошибок, из-за которых сборка
падает на пустом месте: незакрытый `/*`, лишняя тройная кавычка, кириллица в шаблоне без `(?iu)`.

## Подпись и обновления

Debug-ключ лежит в репозитории (`app/debug.keystore`, пароли `android`) и подключён в
`signingConfigs.debug`. Это осознанно: без него каждый GitHub-раннер генерирует свой
`~/.android/debug.keystore`, подписи APK из разных прогонов не совпадают, и `adb install -r`
отказывает с `INSTALL_FAILED_UPDATE_INCOMPATIBLE` — на телефоне продолжает стоять старая версия,
что со стороны выглядит как «новую функцию не сделали». Проверить, что реально установлено, можно в
приложении: «Настройки» → «Установленная сборка: 1.1 (2) — debug».

Если ключ всё-таки сменился, обновиться поверх нельзя — только `adb uninstall com.example.otsled`
с потерей данных (иногда сохраняет `adb uninstall -k`). Воссоздать тот же файл:

```bash
openssl req -x509 -newkey rsa:2048 -sha256 -days 36500 -nodes \
  -keyout key.pem -out cert.pem -subj "/CN=Android Debug/O=Otsled"
openssl pkcs12 -export -inkey key.pem -in cert.pem -out app/debug.keystore \
  -name androiddebugkey -passout pass:android
```

Для публикации в RuStore или Play нужен отдельный release-ключ: в git его не кладут, хранят в
секретах репозитория и подписывают `assembleRelease`. Перед каждым релизом поднимают
`versionCode` — по нему система отличает обновление от отката — и `versionName`.

CI (`.github/workflows/ci.yml`) выполняет обе команды на каждый push.

## Обновления внутри приложения

В «Настройках» — карточка «Обновления»: «Проверить обновление» читает
`api.github.com/repos/<репозиторий>/releases/latest` (публично, без токена), а «Скачать» приносит
`app-debug.apk` в кэш и предлагает файл системному установщику.

Что тут принципиально:

* **версия берётся из заголовка релиза** («Последняя сборка (1.2)»), который пишет CI; если заголовок
  переименован или APK в релизе не выложен, приложение говорит «не удалось проверить», а не
  «обновлений нет» — второе при сломанном парсере означало бы «никогда не обновляемся»;
* **сравнение версий разрядное** (`AppUpdateFeed.isNewer`): строковое сравнение считает «1.10»
  старее «1.9», а номер растёт именно так;
* **проверка и скачивание — два нажатия**: файл весит около 20 МБ, и тратить трафик молча нельзя;
* **скачанный файл проверяется на сигнатуру архива** (`PK` в начале) и на размер: `HTTP 200` не
  гарантирует, что там APK, а не страница-заглушка;
* **установка всегда подтверждается системой**. Нужны `REQUEST_INSTALL_PACKAGES` и `FileProvider`
  (открыт только подкаталог кэша `updates/`); на Android 8+ пользователь один раз разрешает установку
  самому приложению — об этом говорит отдельная кнопка «Разрешение», а не молчаливый отказ;
* автопроверки при запуске нет намеренно: она добавила бы запрос к GitHub на каждый холодный старт.

CI кладёт в релиз два файла: `app-debug.apk` (его перезаписывает каждый прогон — его и берёт
приложение) и `app-debug-<версия>.apk` (не перезаписывается: им удобно поставить или откатить
конкретную сборку). Если в релизе окажется несколько APK, приложение берёт `app-debug.apk`, а не
первый попавшийся.

Файл остаётся в кэше до следующей загрузки (перед новой сборкой старый удаляется: иначе установщик
мог бы молча взять прошлую версию).

## Как устроена проверка цены

Сайт закрыт JavaScript-проверкой браузера, поэтому путь к цене всегда два шага:

1. **HTTP** — `OkHttp + Jsoup` (`AllureParfumPriceParser`). Быстро, но при активированной защите
   вместо товара приходит заглушка с кодом 200.
2. **WebView** — `WebViewPriceFetcher` исполняет JavaScript защиты, ждёт перенаправления
   и забирает цены через `evaluateJavascript`.

`PricePageLoader` выбирает между ними, а `ParseSessionStore` помнит исход: после «проверьте
браузер» следующие проверки идут сразу в WebView, а когда сессия прогрета — снова по быстрому
HTTP. Куки WebView и OkHttp общие (`WebViewCookieJar`), поэтому защита проходится один раз,
а не на каждый товар.

### Почему парсер такой «широкий»

Разметка на Bitrix меняется, поэтому цены ищутся четырьмя стратегиями по убыванию точности:
объём-якоря → строки офферов → текстовые блоки → JSON внутри страницы. Дополнительно:

- блоки «похожие ароматы», «рекомендации», отзывы и подвал вырезаются из документа до поиска,
  иначе цены чужих товаров попадают в отслеживание;
- фрагмент «цена за 1 мл» вычищается — иначе «84 руб. за 1 мл» превращается в фиктивный флакон;
- цена доставки/бонусов отбрасывается по слову перед числом, а не по факту наличия такого слова
  в строке (в одной ячейке могут стоять и цена аромата, и цена доставки);
- минимальная из найденных цен считается актуальной, большая — зачёркнутой: порядок цифр
  в разметке непредсказуем.

Все эти правила покрыты тестами в `app/src/test/.../parser/` — при изменении сайта правки
нужно начинать с них.

### Если сайт не пускает

Фоновый WebView создаётся без окна: автотест сайта он проходит, а капчу или кнопку «я не робот» —
нет. Поэтому в настройках есть «Пройти проверку в приложении» (`ui/challenge/BrowserCheckScreen`):
открывается обычная интерактивная WebView-страница сайта, человек отвечает на вопросы, а куки
остаются в общем `CookieManager` — после этого снова работают и поиск, и фоновые проверки. Там же
показано, что именно выдал сайт («состояние: complete, текста: 4213, ссылок на товары 18» и начало
страницы) — это та самая строка, по которой удалённо различаются автотест, капча и блок по IP.
В debug-сборке включён `setWebContentsDebuggingEnabled`, страницу можно открыть через
`chrome://inspect` и прислать разметку целиком.

Второе правило той же темы: **отказ одного пути не закрывает другой**. Кулдаун после
«проверьте браузер» означает «сначала WebView», а не «только WebView» — если WebView цен не дал,
быстрый HTTP всё равно пробуется (и наоборот, см. `PricePageLoader`, `AllureSiteSearch`). Иначе
одна неудачная проверка блокировала бы и добавление товара, и поиск на целый час. Текст ошибки
проверки теперь дополняется выжимкой со страницы (`BotProtection.stubSummary`), а не ограничивается
словом «кулдаун».

Третье правило той же темы: **«подозрительный ответ» — не то же самое, что «заглушка»**.
`BotProtection.isChallengeHtml` считает страницу блокировкой, только если в ней нет признаков живого
контента (ссылок `/katalog/`, цен, формы поиска) либо она короче `TINY_PAGE_LIMIT`. Раньше хватало
слова «captcha» или «javascript» в разметке — а они есть на любой живой странице, и нормальный диагноз
«сайт запросил проверку браузера» появлялся там, где сайт всё отдал. По той же причине страница поиска
считается готовой к разбору только когда в ней видны ссылки на товары или вердикт «ничего не
найдено» (`SiteSearchQuery.isReadyForExtraction`): первый кадр — это шапка сайта, и по ней вывод об
отсутствии совпадений делать нельзя.

### Ловушка регулярных выражений с кириллицей

В `java.util.regex` флаг `(?i)` без `(?u)` сворачивает регистр **только для ASCII**: шаблон `руб`
с `RegexOption.IGNORE_CASE` не найдёт «22 235 РУБ.», а фильтр мусорных строк не отбросит
«Подробнее». Поэтому в регулярках с русскими буквами внутри шаблона пишется `(?iu)`: `RegexOption.UNICODE_CASE`
в Kotlin отсутствует как класс, а `RegexOption.IGNORE_CASE` сам по себе кириллицу не складывает.
Там, где вход предварительно нормализуют через `lowercase()` (`BotProtection`), достаточно и этого,
но флаг оставлен: нормализация не спасает шаблоны, которым подают сырой текст страницы.
Равенство разбора строк, отличающихся только регистром, закреплено тестами
(`data/parser/CyrillicCaseParsingTest`).

## Данные

Room, три связанные таблицы + кольцевой журнал:

| Таблица | Назначение |
| --- | --- |
| `products` | товар, целевая цена, настройки уведомлений, состояние последних проверок |
| `product_variants` | цены по объёмам; `isTracked = 0` — объём исчез со страницы |
| `price_history` | история изменений цен (привязана к варианту) |
| `price_check_log` | последние проверки: источник (HTTP/WebView), число вариантов, ошибка |

Журнал проверок доступен в настройках — это основной способ понять, «парсер сломался»
или «товар действительно изменился», не подключая adb.

## История и график цены

В карточке товара — график на `Canvas` (без сторонних библиотек) по записям `price_history`:
минимум, максимум, средняя и изменение с прошлой проверки. История пишется только когда цена
реально изменилась, поэтому точка графика = момент изменения, и дата подписана явно.

Ряд считается в `domain/PriceSeries.kt` и покрыт юнит-тестами: кривой график — это ещё и враньё
в цифрах под ним. Формат цен и процентов — `util/PriceFormatter.kt` (неразрывные тысячи, копейки
только если они есть, без `NumberFormat`, чтобы вывод не зависел от локали устройства).

Переключатель объёма относится и к графику, и к списку истории: «все объёмы» — это «цена от»,
то есть минимум по всем вариантам в момент проверки. В списке товаров у каждого товара свой
мини-график (последние 24 точки), а история тянется одним запросом на все товары.

## Поиск товара по названию

На экране «Добавить товар» есть поле поиска: вводим название или бренд, получаем строки выдачи
`allureparfum.ru/search/` и по тапу подставляем ссылку — цены по объёмам подтягиваются сразу,
до сохранения. Никаких ручных копирований URL.

Разбор выдачи (`data/site/SiteSearchQuery.kt`) намеренно не зависит от имён классов: live-разметку
страницы поиска увидеть нельзя (сайт отвечает JS-проверкой браузера), поэтому берутся все ссылки
вида `/katalog/<раздел>/<бренд>/<товар>.html`, а название, цена и объём ищутся вокруг них.
Ссылки из `header`/`footer`/`nav`/`aside` отбрасываются, дубликаты (картинка + текст, пейджинг
`?PAGEN_1=…`) склеиваются, порядок сортировки — по совпадению с запросом.

Название строки берётся НЕ из текста ссылки: в карточке Allure ссылкой является кнопка «Подробнее»,
а бренд и товар подписаны отдельными строками. Поэтому имя собирается по блоку карточки
(ближайший предок, в котором есть цена и нет ссылок на чужие товары) и приводится к виду
«Бренд - Товар». Цены, объёмы, подписи блока («Унисекс», «Семейство: …») и бейджи («ХИТ», «NEW»)
в название попасть не могут.

Путь до страницы — тот же, что у проверки цены: сначала HTTP, при проверке браузера — WebView
(`AllureSiteSearch` + общий `ParseSessionStore`), поэтому «прогретая» сессия ускоряет и поиск.
`readyWhen` для WebView здесь — `SiteSearchQuery.isReadyForExtraction`: страница считается готовой
по ссылкам на товары или по вердикту «ничего не найдено». Первый кадр страницы — это только шапка
сайта, и по ней вывод «совпадений нет» был бы ложью: в этом случае делается второй заход.

Исход каждого поиска пишется в «Журнал проверок» (Настройки) и показывается под результатом:
HTTP-код, размер страницы и число найденных ссылок на товары по каждому пути. Это единственный
способ удалённо различить три очень разных случая — «товара нет», «сайт ответил проверкой
браузера» и «мы не разобрали выдачу». `WebPageContent.challenge` теперь означает «настоящую
страницу так и не увидели», а не «вариантов цен нет»: иначе страница поиска, где цен по
определению нет, ложно сообщала бы о блокировке.

### Чужие блоки на странице поиска

Под результатами сайт отдаёт карусель «Вы смотрели» (иногда «Рекомендуем») — ссылки там выглядят
точно так же, как ссылки результатов: `/katalog/…/<slug>.html`. Отличать их по имени класса
нельзя (живую разметку мы не видим, а шаблон меняется), поэтому правило независимое от вёрстки:
строка остаётся, если в её названии есть хоть одно слово запроса. Так отслеживаемые товары больше
не заполняют выдачу при поиске нового, и список из сорока позиций не превращается в мусор.

Клапаны безопасности:

* если под это правило не попала ни одна строка — не отсеивается ничего. Поиск по артикулу или
  транслитерацией («кирке» против «Kirke») иначе показывал бы «совпадений нет»;
* сколько строк убрано видно в диагнозе под выдачей и в «Журнале проверок»:
  `отсеяно 2 строк не по запросу (в выдаче 3)`. Если при честном названии там большое число —
  значит правило сработало слишком строго, и чинить надо его, а не молча показывать всё.

### Пометка «уже отслеживается» в выдаче

Строка выдачи сопоставляется со списком по каноническому URL (`data/site/SiteSearchTracking.kt`):
обрезка `?PAGEN_1=…`, `#…` и хвостового `/`, относительный адрес в базе и абсолютный в выдаче —
один и тот же товар. Такая строка помечается и по тапу открывает карточку товара, а не заводит
вторую запись: вставка товара с тем же URL идёт через `REPLACE` и молча стёрла бы целевую цену и
настройки уведомлений.

Сколько строк опознано, видно в строке диагноза под выдачей (и в «Журнале проверок»):
`совпало со списком 1 из 3 (в списке 2)`. Совпадений ноль при непустом списке — там же примеры URL
с обеих сторон: сопоставление строгое, и по этим двум строкам сразу видно, разошлись адреса или
товара действительно нет в списке.

## Список: порядок и фильтры

Над списком — две строки чипов: порядок (`Недавние`, `По названию`, `Цена ↑`, `Цена ↓`,
`Сильнее упали`, `Давно не проверялись`) и фильтр (`Все`, `Ниже цели`, `Упала цена`,
`С проблемами`, `Без цены`). Считает это `ProductListOrdering` — чистая функция без Room и без
Compose: сортировать нужно по полям, которых в таблице нет (падение цены берётся из истории),
а список короткий. Отсутствие цены и отсутствие истории уходят в конец (в начало — для «давно не
проверялись»), равные значения сохраняют порядок, чтобы карточки не прыгали при каждом обновлении.
В заголовке видно «Показано 2 из 9», а если под фильтр не попало ничего — отдельный экран с кнопкой
«Сбросить фильтр»: пустой список без объяснения выглядит как потерянные данные.

Порядок, фильтр, показываемые строки и счётчик приходят одним состоянием `ProductListUiState`: по
отдельным потокам они разъезжаются на первом кадре (счётчик ещё ноль, строки уже есть), и экран
выглядит как список без чипов.

Выбор порядка и фильтра живёт в `ProductListViewModel` и не сохраняется между запусками — это
осознанно: сброс после перезапуска безопаснее, чем «список пустой, потому что вчера стоял фильтр».

## Фоновые проверки

По умолчанию `WorkManager` (`PriceCheckWorker`, интервал 15/30/60 минут, ограничение — сеть).
В настройках можно включить `PriceCheckForegroundService` с постоянным уведомлением: он проверяет
чаще, но расходует батарею. Если весь прогон завершился ошибкой (сайт не отдал ни одну страницу),
воркер возвращает `Result.retry()` с экспоненциальной паузой; частичный успех повтора не требует.
